1. 死锁避免的基本思想

死锁的三种处理策略各有侧重：死锁预防（2.4.2 节）通过破坏四个必要条件之一，使死锁根本不可能发生，但往往牺牲了资源利用率；死锁检测（2.4.4 节）则先放任死锁发生，再回头检测与解除。

介于二者之间的，是死锁避免：它在资源分配过程中动态地判断——若本次分配会导致系统进入不安全状态，就暂不分配，让进程等待，从而使系统始终保持在安全状态。死锁避免不破坏四个必要条件，而是用「事前判断」来绕开死锁，因此比死锁预防允许更高的并发度，代价是需要预知每个进程的最大资源需求并付出计算开销。

定义：安全状态与安全序列

所谓安全状态，是指系统能按某种进程推进顺序为每个进程分配其所需的资源，直至所有进程都能获得所需资源并顺利运行完成。此时存在一个安全序列：一个进程的排列 P1, P2, …, Pn，使得按此顺序依次满足每个进程的最大需求，系统都不会因资源不足而失败。若找不到这样的安全序列，则称系统处于不安全状态。

关键结论

① 安全状态一定不发生死锁；② 不安全状态不一定发生死锁（只是「可能」发生死锁，因为进程可能不会一次性申请完最大需求）；③ 死锁状态一定是不安全状态。三者的包含关系为：死锁 ⊂ 不安全 ⊂ 全部状态。

易错点

「不安全状态」与「死锁」不能画等号。处于不安全状态时，只要进程按照安全序列之外的某种顺序申请资源，才可能死锁；若进程恰好没有同时申请到最大需求，也可能平安结束。因此做题时问「是否安全」就要严格找安全序列，找不到才判不安全。

2. 银行家算法：数据结构

银行家算法（Banker's Algorithm）是死锁避免的经典实现。它把系统比作银行家，进程比作借款人，资源比作资金。设系统有 n 个进程、m 类资源，需要维护以下数据结构：

数据结构含义规模
Available系统当前各类资源的可用数量（尚未分配出去的）长度 m 的一维向量
Max每个进程对各类资源的最大需求n × m 的矩阵
Allocation已分配给每个进程的各类资源数量n × m 的矩阵
Need每个进程尚需的各类资源数量n × m 的矩阵
Request进程本次请求的各类资源数量长度 m 的一维向量
关键结论：三个恒等式

① Need[i][j] = Max[i][j] − Allocation[i][j]（每个进程还需要的 = 最大需求 − 已分配）；
② Available[j] = 系统资源总量[j] − Σi Allocation[i][j]（可用 = 总量 − 已分配总量）；
③ 任一时刻满足 Need[i][j] ≥ 0。

3. 安全性算法（判断是否安全）

安全性算法的目标是找出一个安全序列，其核心是维护一个「试探性」的工作向量 Work（初始时 Work = Available）和一个完成标志数组 Finish（初始全为 false）。步骤如下：

① 初始化：Work = Available；Finish[i] = false（i = 0,1,…,n−1）。
② 在所有满足 Finish[i] == false 的进程中，寻找一个满足
        Need[i][j] ≤ Work[j]   (对一切 j = 0,1,…,m−1)
   的进程 i，即“它需要的资源当前都能满足”。
③ 若找到这样的 i：
        令 Work = Work + Allocation[i]；   // 进程 i 结束，归还它已占的资源
        Finish[i] = true；把 i 记入安全序列；
        转回 ②。
   若找不到：
        转 ④。
④ 若所有 Finish[i] 均为 true，则系统处于安全状态，步骤中记录的进程顺序即一个安全序列；
   否则系统处于不安全状态（此时已找出的只是“可完成前缀”）。
记忆口诀

安全性检查记「比 Need、给 Work、标 Finish」：比当前进程的 Need 是否 ≤ Work；满足就让它跑完并归还其 Allocation（Work 加上去）；标记 Finish 并放进序列；重复直到所有进程都能完成。

4. 经典例题（408 高频）

设系统有 5 个进程 P0~P4 和 3 类资源 A、B、C，某时刻的状态如下（已知资源总量为 A=10、B=5、C=7）：

进程Allocation (A B C)Max (A B C)Need (A B C)
P00 1 07 5 37 4 3
P12 0 03 2 21 2 2
P23 0 29 0 26 0 0
P32 1 12 2 20 1 1
P40 0 24 3 34 3 1

此时 Available = 总量 − ΣAllocation = (10−7, 5−2, 7−5) = (3, 3, 2)。按安全性算法检查：

步骤Work (A B C)可选进程完成后 Work += Alloc
初始3 3 2P1 (1 2 2 ≤ 3 3 2)3 3 2 + 2 0 0 = 5 3 2
25 3 2P3 (0 1 1 ≤ 5 3 2)5 3 2 + 2 1 1 = 7 4 3
37 4 3P0 (7 4 3 ≤ 7 4 3)7 4 3 + 0 1 0 = 7 5 3
47 5 3P2 (6 0 0 ≤ 7 5 3)7 5 3 + 3 0 2 = 10 5 5
510 5 5P4 (4 3 1 ≤ 10 5 5)10 5 5 + 0 0 2 = 10 5 7

所有进程都能完成，故系统处于安全状态，一个安全序列为 P1 → P3 → P0 → P2 → P4（即 [1, 3, 0, 2, 4]）。

易错点：如何保证安全序列“唯一/规范”

一个状态的安全序列可能不唯一，考试与判题通常约定：每次在所有可完成的进程中选取下标最小的那个。按此规则本例得到 [1, 3, 0, 2, 4]。若每一步都选最小下标，结果就是确定的。

5. 资源请求算法

当进程 Pi 提出请求 Requesti 时，银行家算法按下列顺序检查，全部通过才真正分配：

① 若 Request[i][j] ≤ Need[i][j]（对一切 j），转 ②；
   否则说明请求量超过了它声明的最大需求，视为出错。
② 若 Request[i][j] ≤ Available[j]（对一切 j），转 ③；
   否则当前资源不足，P[i] 必须等待。
③ “试探性分配”：
        Available  = Available  − Request[i]
        Allocation[i] = Allocation[i] + Request[i]
        Need[i]        = Need[i]        − Request[i]
④ 执行安全性算法。若分配后系统仍安全，则正式分配；
   若分配后系统变得不安全，则撤销试探性分配，恢复原状态，让 P[i] 等待。
关键结论

死锁避免的本质是：每次分配前都做一次安全性预演，只有分配后仍存在安全序列才真正分配。这也解释了它的缺点——需要预知 Max、计算量大、并发度受限。

7. 小结与真题问法

真题典型问法

① 给出一张 Allocation / Max 表，求 Need 与 Available，判断是否安全并写出安全序列；
② 给一次具体请求 Request，问能否分配——先查 Request ≤ Need、Request ≤ Available，再做安全性检查；
③ 判断「不安全状态是否一定死锁」——不一定；「安全状态是否一定不死锁」——一定；
④ 问银行家算法属于哪种策略——死锁避免（不是预防、也不是检测）。

记忆口诀

「Max 减 Allocation 得 Need，总量减 Alloc 得 Available；Work 从 Available 起，Need ≤ Work 就还资源，全部完成才安全。」请求三连问：超没超 Need？够不够 Available？分配后还安全吗？

教材原文（王道）

银行家算法是最著名的死锁避免算法。它在分配资源之前先计算本次分配是否会导致系统进入不安全状态，若不会进入不安全状态，才进行分配。系统处于安全状态时一定不会发生死锁；处于不安全状态时则可能发生死锁。
